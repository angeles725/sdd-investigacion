### merge-gate (phase 8 slice 8.0)

| Tool | Description |
|---|---|
| `rsdd gate merge` (shim: `merge-gate.sh`) | Declared divergence from the frozen bash original (`rsdd/internal/gate/testdata/legacy/merge-gate.sh`), CI gate only: a check in the REQUIRED list (`--required-checks`, else `MERGE_GATE_REQUIRED_CHECKS`, else `shellcheck,toolbelt-tests`) must conclude `success`. The original counted `skipped` and `neutral` as green for every check, so a required check GitHub reported as skipped merged as `ok`; now the latest run of a required name that concluded `skipped` or `neutral` refuses with `refuse: ci_skipped (name[,name])` (names unique and sorted, exit 1). `skipped` and `neutral` stay acceptable for checks outside the required list (`toolbelt-extras` is skipped on every PR). The path-filter exemption (kit issue #1867) only removes a required name that has NO check run at all (its workflow did not run for this diff); a required name that has a run concluded `skipped` or `neutral` is never exempted and is refused. A second declared divergence (kit issue #2852): a workflow job whose `name:` holds a `${{ }}` expression the reader cannot expand (a matrix job such as `rsdd-go-bridge`) no longer makes every required check "not evaluated against path filters" (the original gave up on the whole workflow with `job name shape of <job id>`). The name is read as a set of possible expansions (literal text, string literals and `format()` templates with unknown gaps, `&&`/`||` alternatives, comparisons as `true`/`false`, anything else fully unknown); it still voids the evaluation, fail-closed, for a required check that SOME expansion could equal (no literal part, or its literal parts fit the check name in order at both ends), for an expression the reader cannot delimit or balance, and for more than 64 alternatives or an alternative of more than 32 parts (the trimmed readings are enumerated in O(parts^2), no longer exponentially, so the gate answers in milliseconds for hundreds of expressions). For a required check it cannot be, the job is simply no carrier of that check (even when its id is the check name). The reader decodes no YAML scalar, so the name is judged only when it reads as a plain one-line scalar with no escapes, or a quoted one whose body has none; anything else is "could be anything" and voids the evaluation for every required check (`job name shape of <job id>`): a double-quoted scalar containing a backslash (also without `${{`, since an escape can spell `${{`), a single-quoted one containing a quote (`''` decodes to one quote), an opening quote without the matching closing one (or one cut off by a ` # ` comment), a trailing backslash, a control character (the CR a mixed or CRLF line ending leaves on a `name:` line, a tab, U+2028/U+2029), and a continuation line (the next non-blank, non-comment line is indented deeper than the `name:` key; YAML folds it into the name). The reader looks at one line at a time, so a templated `name:` is also not trusted, for every required check (`job name shape of <job id>`), when the job (a) has more than one `name:` line at the job-key indent (`name: shellcheck` then `name: bridge-${{ matrix.n }}`), or (b) has ANY line, before or after the name line and the job key line included, that leaves a double quote, a single quote or a `[`/`{` open at its end after dropping a ` #` comment outside quotes, or whose value starts with a quote that the line does not close: such a value can swallow a following `name:` line, so that GitHub sees no `name` key and names the check by the job id (`runs-on: "foo` / `name: bridge-${{ matrix.n }}"`; also single quotes, `env: {a: 1,` and `needs: [a,`). The test is deliberately over-approximate (an apostrophe in a plain scalar counts as an opening quote). The content of a block scalar (`run: |`, `path: >-`, `- |`) is skipped, not scanned: it is indented deeper than the key that opens it, so it cannot hide a key at the job-key indent, and the real `rsdd-go-bridge` job stays evaluated. Scope note, differing from the original: a NON-templated double-quoted name containing a backslash (`name: "shell\x63heck"`) now voids the evaluation for every required check (fail-closed; an escape can spell any character of a check name), where the original read it literally and went on. NOT closed by this change (baseline gaps of the line-by-line reader, independent of a templated name, tracked in one follow-up kit issue): a quoted `"name":` key, a flow-mapping job, `? name`, `name :`, `Name:`, `name: null` / `~` with the job id fallback, a non-templated name followed by a CR, a column-0 or tab-led line inside a multi-line scalar that hides later jobs, and a fake non-templated `name:` line inside a multi-line scalar. GitHub's behaviour on the following could not be verified, so each is decided fail-closed: leading and trailing whitespace of an expansion may be trimmed (`shellcheck ` could be `shellcheck`, also when an unknown part may be blank), a whitespace-only expansion may count as empty (the job id fallback applies), and check names compare case-insensitively (Unicode simple folding) for this judgement, also the job id against the check name. Pinned by `TestPathFilterTemplatedJobName*` (`mergepf_jobname_test.go`; the differential test keeps only the shapes both implementations still refuse). Precedence of the CI refusals: `ci_failed`, `ci_pending`, `ci_skipped`, `ci_missing`. The main table row above still describes the rest of the contract; its "success/skipped/neutral" wording applies to non-required checks only. Pinned by `TestCIVerdict` and `TestCISkippedRequiredDiverges` (the original answers `ok`, the port `ci_skipped`); every other CI case stays byte-identical in the differential test. |
